# Нагрузка Portable TPC-C

Модуль запускает [portable-tpcc](https://github.com/zinal/portable-tpcc) с адаптером YDB. Модуль работает параллельно с существующим каталогом `workload/` и не меняет его настройки. Таблицы создаются в отдельном каталоге `TPCC_PATH`.

Исходный код закреплён на коммите `fbf3e642d21b9e18e3a80f86613f025bcf906b8a`. Сборка применяет `patches/standalone-drain.patch`. Патч оставляет 30 секунд для завершения транзакций после измерения и до удаления терминалов.

## Настройка и запуск

Создай локальный `config.local.sh`, который не попадает в Git. Укажи адрес YDB в `TPCC_ENDPOINT`, базу в `TPCC_DATABASE` и каталог таблиц в `TPCC_PATH`. Для защищённого соединения укажи файл удостоверяющего центра в `TPCC_CA_FILE`. Для копирования модуля задай `TPCC_REMOTE_HOST`, `TPCC_REMOTE_USER` и `TPCC_REMOTE_DEST`.

Команда `bash deploy.sh` копирует модуль и дашборд через одно SSH-соединение. Команда `bash deploy.sh --dry-run` показывает состав архива без подключения. На машине генератора выполни команды из каталога модуля:

```bash
bash build.sh
bash tpcc.sh info
bash tpcc.sh schema 3000
bash tpcc.sh import 3000 5
bash tpcc.sh indexes 3000
bash tpcc.sh run 3000 5 256 20
```

Числа в примере задают 3000 складов, 5 потоков генератора, предел 256 одновременно выполняемых транзакций и 20 минут измерения. Число складов требуется подобрать под ресурсы базы. `inflight` задаёт внутренний параллелизм транзакций, а не число потоков или ядер процессора.

При `TPCC_WARMUP_MIN=0` генератор выбирает адаптивный прогрев. Для более 1000 складов прогрев составляет 30 минут. Паузы ввода и обдумывания включены по умолчанию: `TPCC_NO_DELAYS=false`. Режим `serializable-rw` можно заменить через `TPCC_TX_MODE`, если база поддерживает выбранный режим записи.

Для аутентификации по логину задай `TPCC_AUTH_SCHEME=login` и `TPCC_USER`. Пароль передай через переменную окружения, имя которой задаёт `TPCC_PASSWORD_ENV`. Локальные настройки и пароли не включаются в коммит. Для удаления выделенных таблиц требуется явное подтверждение:

```bash
TPCC_CONFIRM_DROP=YES bash tpcc.sh drop 3000
```

## Метрики и результаты

Команда `tpcc.sh run` сохраняет журнал и передаёт показатели в VictoriaMetrics каждые пять секунд. Серии имеют префикс `tpcc_workload_`; метка `application` задаётся через `TPCC_APPLICATION`. Дашборд `Portable TPC-C Chaos` показывает скорость транзакций, ошибки, задержки и ресурсы генератора. Генератор выбирается переменной дашборда `load_host`. Метрики ресурсов требуют установленного node_exporter и настроенного сбора в VictoriaMetrics.

Скорость и ошибки относятся к интервалу вывода статистики. Девяностый перцентиль задержки, p90, накапливается в пределах фазы измерения. Значение p90 нельзя интерпретировать как задержку только за выбранный интервал хаоса. Итоговый tpmC считает New-Order по правилам генератора, включая пользовательские откаты; `analyze-log.sh` считает общую скорость только по транзакциям с кодом `OK`.

Команда `evaluate-run.sh ЖУРНАЛ` читает итоговый блок генератора и оценивает efficiency и p90 каждого типа транзакций. Подробная методика приведена в [EXPERIMENT.md](EXPERIMENT.md).

Исходники, бинарник, журналы и результаты по умолчанию сохраняются в `out/workload-portable-tpcc/`. Каталог можно переопределить через `TPCC_OUT_DIR`, исходники через `TPCC_SOURCE_DIR`, журналы через `TPCC_LOG_DIR`.

Команды `check-import` и `check-test` запускают проверки согласованности из исходного проекта. Проверка таблицы `history` фильтрует по полю вне первичного ключа и может выполнять дорогие сканирования на больших наборах. Успешная загрузка и выборочные проверки не заменяют полную проверку согласованности.
